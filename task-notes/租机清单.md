# 租机清单：内核四题（210 分）唯一真正的门槛是一台能编译 seekdb 的 Linux

> 结论先说：**要租，租一台 8 vCPU / 32 GB / 100 GB SSD 的 Ubuntu 22.04 或 24.04 x86_64，先租 1 天做可行性探测。**
> 不需要 GPU。判题平台自述「seekdb 2 并发约 30 分钟编译」，那就是官方编译机的量级，照着租即可。
> 我这边（Windows，无 VS/MSVC/Windows SDK/clang/cargo）已经在三个不同方向上证伪了「不编译也能验 C++」：
> 见 `D:\比赛\00-台账\交接文档.md` §14.1。

## 1. 为什么必须是 Linux

| 缺口 | 证据 |
| --- | --- |
| 官方 Windows 路线要 VS 2022 Build Tools + Windows SDK | `docs/developer-guide/en/toolchain.md:112`；本机 `vswhere.exe` 不存在、`Windows Kits\10\Include` 无 |
| 任何 `src/sql/**.cpp` 都硬依赖 cargo 生成物 | `src/sql/ob_sql_utils.h:20` 无条件 `#include "config_bridge.h"`，而它是 cxxbridge 生成的（`rust/exports.json`），本机无 cargo |
| 还需要 build 期生成的 inner-table 头 | `src/CMakeLists.txt` 的 `${CMAKE_BINARY_DIR}/generated/**`，由 `generate_inner_table_schema.py` 产出 |
| 语法层要在**判题同款 bison** 下才算最终确认 | `src/sql/parser/gen_parser.sh:29-34` 钉 **2.4.1** 且用 `-Werror`；而 `deps/init/oceanbase.el9.x86_64.deps` 里正好有 `obdevtools-bison-2.4.1`（还带 flex 2.5.35 / gcc 12.3 / llvm 17 / cmake 3.30）⇒ **`--init` 之后现成可用，不用自己装** |

Ubuntu 不是障碍：`deps/init/dep_create.sh:108` 把 ubuntu ≥ 22.04 映射到 **el9** 依赖档，所以官方依赖包能直接拉下来。

## 2. 到手后按顺序执行（前 6 步总共约 10 分钟，第 7 步才是长活）

```bash
# 1) 基础工具
sudo apt update && sudo apt install -y git curl python3 build-essential

# 2) 拉源码（匿名 HTTPS 可读；判题目标分支是 2026-competition）
git clone --branch 2026-competition https://github.com/oceanbase/seekdb.git seekdb
cd seekdb

# 3) 取我这 14 份补丁草稿与题面（独立分支，孤儿树，只有文档和 .patch）
git clone --branch draft/kernel-patches --depth 1 \
    https://github.com/dfbkfbklmslMBl/seekdb.git kbundle
#   kbundle/kernel-patches-draft/{file-sql,ai-fn,ai-column,fts-opt}/*.patch
#   kbundle/task-notes/{题面/,验证流程.sh,编译环境-两条路线.md,补丁语法二分.sh}
```

**第 4 步编译出 `compile_commands.json` 之后，先跑这份脚本再决定往哪使劲**（它用 `build.sh:203`
就设了的 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`，只对每份补丁改到的翻译单元跑 `-fsyntax-only`，
一份几十秒，不用等整库编译才暴露一个语法错）：

```bash
PATCH_DIR=~/kbundle/kernel-patches-draft bash ~/kbundle/task-notes/补丁语法二分.sh
```

它会自己区分两类补丁：改 `.cpp/.h` 的（可这样验语法）与改**生成物输入**的 —— ai-column 那四份改的是
`ob_inner_table_schema_def.py` / `ob_errno.def` / `ob_system_variable_init.json` / `.y`，
它们的正确性要靠生成步骤本身（bison/flex 见下面第 6 步），脚本会明确标注「不在本脚本判定范围」而不是假绿。

```bash

# 4) 依赖 + 工具链（含 bison 2.4.1）；这一步会从 mirrors.oceanbase.com 拉几个 GB
./build.sh release --init

# 5) 如果 --init 没有代管 Rust，再手动装（rust/rust-toolchain.toml 已钉 1.98.1 + minimal + clippy）
command -v cargo || { curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain 1.98.1; }
. "$HOME/.cargo/env"; rustc -V   # 期望 1.98.1

# 6) ★ 先把 50 分题的语法层钉死（不用等整库编译，几分钟）
deps/3rd/usr/local/oceanbase/devtools/bin/bison -V | head -1     # 期望 bison (GNU Bison) 2.4.1
cd src/sql/parser
../../../deps/3rd/usr/local/oceanbase/devtools/bin/bison \
  -v -Werror -d sql_parser_mysql_mode.y -o /tmp/base_tab.c       # 基线必须先干净通过
git apply /home/$USER/kbundle/kernel-patches-draft/file-sql/01-file-sql-parser-table-fn.patch
../../../deps/3rd/usr/local/oceanbase/devtools/bin/bison \
  -v -Werror -d sql_parser_mysql_mode.y -o /tmp/patch_tab.c      # 这条过了，语法层就是终局确认
git checkout -- sql_parser_mysql_mode.y non_reserved_keywords_mysql_mode.c \
                ../../query/api/query/parser/ob_item_type.h      # 验完还原，别污染工作树
cd ../..

# 7) 整库编译（这才是长活，30-90 分钟量级）
./build.sh release --make -j"$(nproc)"
```

## 3. 我已经用 win_bison 3.8.2 验过的部分（云上只需复跑，不必重写）

- 补丁可干净应用（`patch -p1` 三文件全过，无 fuzz/offset）；
- 打补丁后 **0 conflict**、**告警逐条与基线相同（各 7 条，去掉行号后签名一致）**；
- 新产生式**可达**：`| file_table_expr { $$ = $1; }` 接在 `table_factor:` 块尾，与既有 `unnest_expr`/`hybrid_search_expr` 同款；
- 生成的 tab.c 里 READ_CSV 命中 8 次 ⇒ 确实进了 LALR 表；
- 已知无害项：`NULLSTR` 声明了却没有产生式使用（属于还没写的 COPY 补丁）——2.4.1 没有 unused-terminal 告警，但建议连同 COPY 补丁一起交，或先删那两行。

**云上第 6 步要确认的只有一件事**：2.4.1 + `-Werror` 下是否仍无冲突/无新告警（3.8.2 与 2.4.1 的歧义判定基本一致，但不能替它签字）。
