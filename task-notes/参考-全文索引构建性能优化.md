# OceanBase 全文索引构建性能优化

来源：语雀 wiki hc3pio/qpbdgg2geoh5zoyx（2026-11-01 抓取，赛题四官方优化讲义）

背景 全文索引是让数据库具备高效文本检索能力的关键基础。对于少量数据，构建索引可能只是一个简单的后台任务；但在真实业务中，文档数量可能达到百万、千万甚至更大规模，文本内容也可能非常长。这时，全文索引构建就会变成一个复杂的系统工程问题：如何读取数据，如何分词，如何生成倒排结构，如何合并中间结果，如何控制内存和 I/O，如何提升并行度，都会直接影响索引构建的耗时和稳定性。 如果全文索引构建太慢，业务就很难快速上线检索能力；如果构建过程资源消耗不可控，还可能影响在线数据库服务。因此，全文索引不仅要“能构建”，还要“构建得快、构建得稳、构建过程可观察、可优化”。这也是数据库系统从功能可用走向生产可用必须跨过的一道门槛。 本题希望同学们从性能优化的角度理解全文索引的内部构建流程。相比前两个偏功能扩展的题目，这个题目更接近数据库内核工程实践：需要分析执行链路，定位性能瓶颈，并思考并行、批处理、内存管理、I/O 和数据结构等因素如何共同影响系统表现。通过这个题目，同学们可以体会数据库系统中“功能正确”和“工程可用”之间的距离。 一、总体架构 本次优化对全文索引构建链路进行了全面的性能提升，涵盖以下六大方面： 分词器/解析器热路径优化 -- 减少逐字符处理中的内存分配和函数调用 排序框架重构 -- 从单体实现拆分为模块化策略架构，SQL 层与存储层共享 FTS 构建流水线重设计 -- 引入分区本地构建模式和多阶段 DAG 任务图 Sort Key 编码优化 -- 支持 encoded sortkey 实现 O(n) 基数排序 Position List 编解码器 -- 新增词位置信息的紧凑编码支持 DDL DAG 监控体系 -- 可观测全文索引构建各阶段进度 二、分词器/解析器优化 2.1 高性能数据结构 数据结构 说明 ObFastSegmentArray 分块数组，使用 2 的幂次块大小，通过位运算实现 O(1) 索引访问。 reuse() 仅重置计数器而不释放内存。替代 ObList 存储分词结果，消除每文档数千次的逐元素堆分配 ObFastList 基于 ObFastSegmentArray 作为节点池的双向链表，保留链表的排序插入/删除语义，但节点从连续内存块分配。用于 IK 分词器的热路径 token 排序链 2.2 关键优化点 合并字符分类调用 : 将 current_char() + current_char_type() 合并为 current_char_and_type() ，将 first_valid_char() + classify_first_char() 合并为 classify_first_valid_char() ，逐字符处理循环中的函数调用减半 解析器实例复用 : 所有解析器（IK、ngram、ngram2、beng、whitespace）新增 reuse_parser() 接口，在文档间重置内部状态并回收临时内存，避免反复构造/析构 内存分离 : 分配器拆分为 metadata_alloc_ （长生命周期的解析器对象）和 scratch_alloc_ （逐文档临时内存，批次间重置），减少内存碎片 缓存函数指针 : well_formed_len 字符集函数指针在初始化时缓存到 TokenizeContext ，避免逐字符的虚函数派发 IK 歧义裁决器复用 : ObIKArbitrator 改为持久化成员通过 reuse() 复用，避免每批次重建 hashmap 2.3 模块重构 ObFTWord / ObFTWordMap 重命名为 ObFTToken / ObFTTokenMap ，支持缓存 hash 值和比较函数指针 新增 ObFTTokenProcessor 替代 ObAddWord ，将最小/最大过滤、停用词检查、大小写转换、token 分组整合为流水线处理，支持提前短路返回 新增 ObStopTokenChecker ，使用进程全局单例 ObStopTokenCheckerGen 延迟生成按 collation 分组的 hash 表，采用无锁模式和预计算 hash 实现 O(1) 查找 三、排序框架重构 3.1 架构变更：单体 -> 模块化 旧实现将所有排序逻辑（算法选择、内存管理、chunk 构建、外部归并、行存储）内联在 ObSortVecOpImpl 中。新系统拆分为以下独立组件： 3.2 策略模式排序算法 ( ObISortStrategy ) 策略 说明 ObFullSortStrategy 标准排序，支持 encoded key 优化。定长二进制键可启用 FixedKeySort （基数排序，O(n) 性能），回退使用 boost::spinsort ObPartitionSortStrategy 基于 hash 的分区排序，每个分区独立排序，避免全局排序开销 ObPartitionTopNSortStrategy 分区 + TopN 联合优化 3.3 资源管理层次 ( ObSortResourceManager ) 基类 ObSortResourceManager : 自适应内存扩展、基于层级的归并扇入计算、dump 决策 SQL 层 ObSQLSortResourceManager : 增加分区 hash 表和 TopN 过滤的内存核算 存储层 ObStorageSortResourceManager : 轻量级变体，用于 compaction 和直接加载操作 3.4 其他核心组件 ObSortChunkBuilder : 模板参数化的 chunk 构建器，支持可插拔 Slicer（单 slice / 多 slice）， ObSortChunkMultiSlicer 支持范围分区输出用于并行 DML ObExternalMergeSorter : 独立的外部归并排序器，使用静态 ObBinaryHeap<MAX_MERGE_WAYS=256> 进行 k 路归并 ObSortRowStoreMgr : 封装 sort-key + addon 列分离模式，归并阶段仅读取 sort key，输出时才物化 payload 列，减少 I/O ObStorageVecSortImpl : 存储层专用排序实现，支持向量化批量 I/O（零拷贝 ObIVector 输出） 3.5 Dump 策略函子 NormalDumpStrategy 、 IMMSDumpStrategy 、 PartitionTopnDumpStrategy -- 通过模板参数传递，编译器可内联，消除虚函数派发开销。 四、FTS 构建流水线 4.1 分区本地构建模式 当表不需要 doc_id 列且非广播/复制表时，全文索引构建（采样、分词、排序、写入）在每个 tablet 内本地完成，无需跨分区数据 shuffle，消除独立的 word-doc DDL 子任务。 4.2 多阶段 DAG 任务图 ObColumnClusteredDag::generate_partition_local_fixed_tasks() 构建以下依赖链： 4.3 FTS 采样流水线 ( ObFtsSamplePipeline ) 两阶段流水线： ObFtsForwardInvertSampleOperator : 从 PX 扫描线程收集采样范围键，转换为列式向量，使用 ObStorageVecSortImpl 排序（支持外排落盘），然后等深下采样（每 N 个键取一个）生成正排索引（doc_id 序）和倒排索引（word 序）的范围边界 ObFtsWriteInnerTableOperator : 将计算出的范围边界持久化到内部元数据表，支持崩溃恢复幂等性。重启时直接读取已持久化的边界而非重新计算 PX 扫描线程通过 ObThreadCond 调用 wait_sample_finish() 阻塞，直到流水线通过 notify_sample_finished() 广播完成。 4.4 自挂起并行归并排序 ObDDLMergeSortTask 实例在同一 slice 上并发运行，原子地弹出已排序的 chunk 子集、归并、推回结果。返回 OB_DAG_TASK_IS_SUSPENDED 以重新调度，直到 chunk 数降至 final_merge_ways 以下，实现无需创建新任务的迭代归约。 4.5 全文索引写入流水线 ( ObFullTextIndexWritePipeline ) 从 ObDDLSlice 的并发 LightyQueue 消费 chunk Sort-flush 算子将列序从 (doc_id, word) 重排为 (word, doc_id) 以满足倒排索引排序要求 Macro-block-write 算子使用 ObCgMacroBlockWriter 高效构建 SSTable 4.6 排序提供者 ( ObDDLSortProvider ) 管理线程级和 slice 级排序句柄，带复用池（互斥锁保护的 reuse_queue_ ）。根据内存预算动态计算归并路数（16MB / block_size，最小 2）。支持 encode-sortkey 优化。 五、Sort Key 编码与位置列表 5.1 Encoded Sort Key ( ObDDLEncodeSortkeyUtils ) 将多列排序键编码为单个二进制串（order-preserving encoding），支持 memcmp 直接比较 ObFtsSegmentSort 专门用于全文索引的 token 排序，将 token hash map 中的数据编码后进行内存排序 定长编码键（2-18 字节）可启用基数排序，实现 O(n) 排序性能 5.2 Position List 编解码器 ( ObFTSPositionListStore ) 新增 T_FUN_SYS_POS_LIST SQL 表达式算子，支持在 FTS 辅助表中生成词位置列表 FTS 辅助表（倒排索引表和 doc-word 表）支持 5 列结构（含位置信息） 使用变长整数编码（ encode_with_variable_int64 ），预留 delta + zigzag + PFor 编码（ encode_with_delta_zigzag_pfor ，待启用） 带 magic number（ 0xFACE ）、版本号和校验和的自描述存储格式 六、SQL 执行计划优化 6.1 Granule Iterator 适配 新增 ObGranuleFtsUtil 支持 FTS 正排范围获取和 slice 索引计算 Granule Iterator 扩展支持 FTS 专用的任务划分和范围分配 6.2 并行 DDL 计划优化 ObDelUpdLogPlan 新增对 fts_doc_word_aux 表的特殊处理，构建倒排排序键以支持正确的并行 SSTable 插入 DocidCompare 比较器支持按文档 ID 进行范围数据重分布，确保各 PX worker 写入不相交的 doc-ID 范围 6.3 StatCollector 扩展 ObStatCollectorOp 增加 FTS 采样相关逻辑，配合 FTS 采样流水线收集范围统计信息 七、DDL DAG 监控体系 7.1 三层架构 层级 组件 说明 管理层 ObDDLDagMonitorMgr 租户级单例（MTL 生命周期），管理监控节点 hashmap，上限 100K 节点，24 小时 TTL，60 秒周期清理。使用 16MB 上限的 FIFO 分配器 节点层 ObDDLDagMonitorNode 每个独立 DAG 执行对应一个节点，以 (dag_ptr, trace_id) 为键，追踪 DAG
